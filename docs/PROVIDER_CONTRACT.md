# 图片 Provider 能力契约（v1）

## 基线

Companion Kit 的图片质量基线固定为：

- 实际上游模型：`gpt-image-2`；
- 请求画质：`high`；
- 支持参考图编辑，以维持固定人物形象；
- 能把生成结果安全返回当前任务或当前入站会话。

缺少任一项时，照片能力关闭，但聊天和原有问题解决能力继续工作。不得静默改用其他模型、占位图片或不明网关。

## 四种宿主是独立选项

用户可以只安装一个宿主，也可以安装多个；不要求四个同时存在。每个安装单独探测、配置和显示状态：

- Codex：优先使用当前任务明确提供的原生图片能力；结果只返回当前任务。
- OpenClaw：优先使用宿主已配置且满足契约的原生图片能力；结果只回复当前入站会话。
- Hermes：优先使用宿主已配置且能证明上游能力的图片路径；宿主别名不能替代实际上游模型证明。
- Claude：只有当前环境安装了满足契约的图片工具、MCP 或 Provider 时才开启；结果只返回当前任务。

如果宿主没有合格的原生能力，可由用户单独配置 OpenAI API 路径。凭据留在宿主密钥库、系统凭据库或环境变量中，Companion Kit 只接收“已就绪”的能力声明，不保存和回显密钥。

## 路由声明

每次选择必须先传入不可由聊天内容覆盖的 `expected_host`，候选列表也只能包含该宿主的路由；任一路由宿主不匹配时整次选择失败。每条候选路由必须声明：

- `host` 与稳定的路由 `id`；
- `kind`：`host_native`、`openai_api` 或 `compatible`；
- `available` 与 `auth_ready`；
- `requested_model`、`upstream_model`、`requested_quality`；
- 是否支持参考图编辑、是否能返回结果；
- 证明级别 `proof`：`verified`、`host_managed` 或 `unverified`；
- 可用时记录回执中的 `reported_model` 与 `reported_quality`。

`compatible` 表示协议兼容但上游不可独立验证，只能在用户明确开启后参与普通模式选择，且永远标记为 `unverified`。

## 选择规则

普通模式按以下顺序选择第一条合格路由：

1. 满足基线的宿主原生路由；
2. 回执可验证的 OpenAI API 路由；
3. 用户明确开启、声明满足基线但上游不可验证的兼容网关。

严格一致性模式只接受回执同时证明 `gpt-image-2` 和 `high` 的路由。没有合格路由时返回 `no_eligible_gpt_image_2_route`，不自动重试到其他模型。

初始化面板后续应把这套判断翻译成三个易懂状态：“可直接使用”“需要配置”“无法验证，默认关闭”，并提供一次由用户主动触发的测试。探测本身不得产生付费请求。

## 固定人物原型图

模板只提供通用的虚构成年人外观文字，不携带任何真人照片。第一次建立固定形象时，建议流程是：

1. 用户选择模板并确认外观描述；
2. 用户主动点击“生成候选原型”，才调用选定 Provider；
3. 使用 `gpt-image-2`、`high` 生成少量候选，不自动发送到聊天；
4. 用户选定一张后将其标记为 `identity_version` 对应的参考资产；
5. 后续照片使用该参考资产进行编辑，并记录所用身份版本。

用户也可以主动提供有权使用的参考图。上传前必须说明图片将发送给所选 Provider，清除 EXIF/GPS，限制格式与尺寸，并允许用户替换或删除整套参考资产。上述原型生成和资产库仍属于后续执行阶段，当前版本只冻结契约。

## 图片任务状态

照片任务使用单向状态机：

```text
planned → authorized → generating → generated → delivered
   └──────────────→ cancelled
   └──────────────→ failed
```

生成成功与投递成功分开确认。取消后到达的迟到结果不得再次投递；事件型宿主必须在生成前保存当前回复目标，桌面型宿主只能返回当前任务附件或本地制品。

## 失败与日志

- 用户看到的是自然、简短的失败说明，不能收到路由内部状态刷屏。
- 日志只记录任务 ID、状态、错误代码、模型证明和耗时；不记录聊天正文、完整图片提示词、参考图路径、凭据或联系人。
- Provider 的数据使用和保留由其条款控制，不属于 Companion Kit 可彻底删除的范围，界面必须在首次外发前说明。
