# Companion Kit 产品逻辑

## 这次只解决 Codex

Companion Kit 的长期目标仍是让常用智能工具都能安装一个轻量陪伴层，但当前版本只把 Codex 当作产品目标。OpenClaw、Hermes 与 Claude 的已有适配不删除，也不在本轮增加功能。

各宿主继续保存各自独立的 Persona、关系和图片目录。本轮不设计统一 Persona，也不做跨宿主同步。

Codex 适合作为第一站，因为它已经有成熟的任务能力和内置图片生成。项目只需处理三件事：人物是谁、关系如何影响闲聊、怎样稳定地生成同一个人物，而不必再造一套聊天和工具平台。

## Persona 是一张轻量人物面板

Persona v3 不再只有 `soul + memory`。它分为几组用户容易理解、程序也能稳定读取的信息：

- 人物总意图：用户最初用一句话描述的期待；
- 表达层：称呼、性格、说话方式、背景基调、重视的事、兴趣和边界；
- 任务层：遇到代码、分析和其他正事时怎样协助；
- 外观层：人物气质与照片默认风格；
- 身份层：是否已经确认脸部身份、身份版本和唯一参考 ID；
- 关系层：相处起点、关系方向和当前多维投影；
- 来源层：哪些字段由系统补全，哪些字段由用户亲手修改。

初始化允许两种入口。用户可以从模板开始，也可以直接输入“高冷御姐，成熟自信，解决问题利落”这样的描述。补全器会生成一份相互协调的草稿，先预览，再由用户确认保存。模板只是起点，不是角色清单。

用户改过的字段会进入 `user_fields`。下次根据新描述重新补全时，这些字段默认保留，避免一次重算把用户慢慢调好的设定覆盖掉。

外观身份是可选项。保存 Persona 后，用户可以直接在面板上传一张参考图；不知道想要什么长相时也可以跳过，直到第一次自然地请求照片。

## 任务质量防火墙

Persona 是表达上下文，不是新的执行器。Codex Runtime 明确要求：

- 代码正确性、事实、安全、测试和用户当前技术要求优先；
- Persona 只改变不关键的表达，不改变工具选择和技术判断；
- 不把背景基调扩写成虚构的现实履历或共同经历；
- 不依赖、不读取也不修改 Codex 全局个性化与记忆设置。

因此同一个对象既可以自然闲聊，也可以继续完成 Codex 原来擅长的任务。

## 关系是多维投影

长期关系由熟悉度、信任度和亲近度组成，短期气氛单独保存并带有效期。关系变化依赖少量结构化事件，同类事件有冷却时间，每天有变化上限。

关系投影只影响闲聊的主动程度、称呼和照片表达上限，不影响任务答案的正确性。长期维度不会因为几天没聊天机械下降，一次小摩擦也不会永久改变所有状态。

当前版本已经能读取和投影关系，但还没有从真实聊天自动产生关系事件。下一阶段的事件提取器只能提交事件类型、置信度、时间和不透明作用域，不得保存聊天正文，也必须区分“用户在抱怨代码”和“用户在表达对人物的不适”。低置信度事件拒绝写入。

## 固定的是脸，不是造型

图片身份和普通成图分开管理。

当 Persona 还没有固定脸，可以在面板直接选择参考图，也可以等第一次照片请求再进入轻量确认流程：

1. 用户上传有权使用的成年人物或虚构形象参考；或
2. 用户描述想要的感觉，由 Codex 内置生图生成；或
3. 由人物根据 Persona 自己决定候选。

面板入口先在浏览器显示预览，转换成 PNG 后进入本地候选槽；聊天入口先在当前任务展示候选。两条入口都不会自动固定，只有用户明确确认后，候选才会成为当前身份版本的主脸参考。Persona v3 仍只保存这一条主脸 `reference_id`，不把侧脸、体型或真实路径写进人格配置。

私有图片资产层以 `profile_id + identity_version` 保存一个轻量 Identity Pack：一张必需主脸，以及可选的一张侧脸和一张体型参考。初始化和首次确认不要求三视图；用户明确要求提高稳定性时，才基于主脸逐张生成补充候选，仍需展示并确认。普通日常成图不得自动收入身份包。

后续任务平时只加载轻量 Persona。真正出现人物照片请求时，`UserPromptSubmit` 才安全解析当前 Identity Pack，把已验证的角色和本地 PNG 路径放进当轮私有上下文。图片调用前，`PreToolUse` 会重写实际工具参数：普通自拍只使用主脸；明确侧脸时使用主脸加侧脸；全身、穿搭、姿势或远景使用主脸加体型；同时涉及侧脸和全身时优先体型。每次最多两张且主脸必带，不把三张同时注入。

未配置可选角色不算错误，继续只用主脸。身份包已经声明的任一成员缺失、损坏、被替换或与当前 Persona 不匹配时，整包失败关闭，不允许忽略损坏成员、跨版本查找或用纯文字重建另一张脸。真实图片工具是否实际接收所选参考，需要单独的端到端验收，不能只凭上下文字符串判断成功。

身份约束只覆盖稳定面部结构、辨识特征和经确认的稳定体型特征。发型、表情、妆容、服饰、姿势、镜头、场景与光线都是动态呈现，应随本次需求变化。当前不做隐藏试拍或自动相似度打分；成图如果明显像另一个人，只在用户明确要求后使用同一组参考重试。

参考图复用可以显著提高一致性，但生成模型不能保证数学意义上的像素级同一。本地资产层能强制唯一身份包、清单完整性和损坏失败关闭，`PreToolUse` 也把实际工具输入限制为一至两张权威参考。自动测试已经覆盖参数重写；不同 Codex 版本是否仍使用相同工具契约，以及最终相似度如何，仍要做真实端到端验收。

## Codex 图片只有一条路径

人物候选、日常照片和参考图编辑都使用 Codex 内置图片生成。Codex 官方说明中，内置能力使用 `gpt-image-2` 并计入现有 Codex 使用额度。

Companion Kit 的 Codex 路径：

- 不读取或索要 `OPENAI_API_KEY`；
- 不展示 Provider、快速/严格模式或独立 API 付费确认；
- 不让用户编写图片提示词；
- 场景不明确时，由人物在 Persona、关系和安全边界内选择普通生活场景；
- 场景明确时直接生成，不重复追问服装、动作和模型参数；
- 没有真实图片结果时，不声称已经拍好或发送成功。

从聊天进入候选槽时，暂存和确认命令只在照片回合私下提供给 Codex，用当前 `session_id` 作为不透明任务作用域。图片工具完成后，专用 `PostToolUse` Hook 只从工具回执提取 `generated_images` 路径，并保存任务、路径、内容和工具调用的哈希。暂存时必须消费同一任务的单次回执；旧任务图片、被替换文件和重复消费都会失败。内部命令、资产 ID、本地路径和图片提示都不得进入人物回复。

面板上传不伪造图片工具回执。浏览器只处理用户当次选择的 PNG、JPG 或 WebP，限制原图大小和最长边，重绘为 PNG；写入接口同时要求本次面板令牌、同源请求和图片使用权确认。服务端只接收图片字节，不接收任意文件路径，并在保存前再次执行 PNG 解码、尺寸限制和元数据清洗。确认主脸使用与聊天入口相同的提交与回滚逻辑。

## 为什么使用窄 Hook

Skill 适合显式调用一项流程，陪伴对象却应该在普通对话开始前已经存在。每次先输入 `$virtual-companion`，产品会立刻变成“调用功能”。

Codex Plugin 使用四个窄 Hook。`SessionStart` 只在新任务开始或恢复时注入压缩后的 Persona 和关系分寸；`UserPromptSubmit` 用本地规则快速判断当轮是否是人物照片，不匹配就零输出，匹配时只签发短期不透明票据；`PreToolUse` 只有在票据、当前回合控制信封和 Persona 全部匹配时才改写参考图参数；`PostToolUse` 只登记真实图片结果，并把同一张照片的文案线索交回 Codex。它们不保存聊天正文，也不把每条普通消息写入磁盘。

Plugin 安装状态与运行就绪状态是两回事。面板按顺序显示：未安装；已安装、待用户在 `/hooks` 审核；用户已确认完成审核、待新任务验证；当前 Persona、主脸和 `SessionStart` 均验证后才是可使用。Codex 没有给面板安全的信任查询接口，因此“我已完成审核”只是用户进度确认，不伪装成 Codex 信任；真正的运行证据只能来自 Hook 自己的健康回执。

`SessionStart` 成功执行后写入最小回执。面板还会比较回执时间与当前 Persona、Identity Pack 的修改时间：如果主脸是在旧回执之后确认的，仍会显示“参考图已保存，但新任务尚未加载”。Plugin 版本或四个 Hook 中任一内容变化时，bundle 摘要会改变，旧审核进度和回执自动过期。`PostToolUse` 只在第一次真实图片结果登记成功后验证，它不阻塞已有主脸的跨任务加载。

Hook 的失败边界是：

- 没有配置时不向任务输出 Persona 内容，但仍可写一张不含私人数据的 `SessionStart` 健康回执；
- 配置损坏时不阻断 Codex；
- 不设置可见状态消息；
- 常驻会话上下文限制在 1400 字符以内；身份路径、照片配方和候选命令只在人物照片回合按需加载，并限制在 3200 字符以内；
- 图片回执只保存哈希和时间，最长保留两小时，不保存原始任务标识或绝对路径；
- 照片回合票据只含受控模式、不透明摘要和时间，二十分钟失效；最近图片类型摘要同时绑定路径与文件内容哈希，两小时失效。已签发的人物编辑票据在任一核验失败时停止，不降级为普通图片编辑；
- 路径只进入模型私有上下文，不在用户回答中展示；
- 安装或变更后仍需用户按 Codex 官方机制检查并信任 Hook。
- 健康回执只保存 schema、Plugin 版本、Hook bundle 摘要、Hook 类型和最近成功时间；不保存聊天、提示词、任务 ID 或参考图路径，也不写入 `trusted_hash`。

Codex Plugin 不再暴露独立诊断 Skill；配置和能力检查走本地面板或 CLI。源码中的 Skill 只保留给 OpenClaw、Hermes 和 Claude 的兼容安装。

## 保持轻量的方法

- Web 面板负责创建、查看、调整 Persona，可选地上传并确认一张主脸，以及安装 Codex Plugin；
- Persona 使用版本化 TOML，关系使用结构化 SQLite，不建立聊天数据库；
- 图片只保留一个候选槽和一个最多三张、角色固定的轻量 Identity Pack，不做图库；另外只保存最近四条受控 PhotoMoment，用于避免连续重复造型，不保存图片或聊天；
- 生成仍由 Codex 完成，项目不再包一层图片 Provider；
- Content Studio 等较重项目只提供分层思路，不复制其工作流和数据模型；
- 当前迭代不为了未来多宿主抽象而增加 Codex 用户看不懂的配置。

## 当前诚实边界

`0.7.0-dev.7` 已完成 Codex 的 Persona v3、一句话草稿、Plugin-only 安装入口、四个 Hook 的审核引导与运行回执、轻量会话加载、按需照片上下文、面板参考图上传、实际图片参数保护、当前任务图片回执、候选确认、跨任务参考图、照片配方去重和图文联动，以及不会覆盖正式数据的本地升级。升级前分别校验用户恢复点和旧程序快照，切换后的健康检查失败时只恢复 Plugin；数据恢复仍只允许复制到新目录。Codex 安装器不会检查或改动用户级 Skill 目录。自动关系事件、Git 来源自动更新和自动卸载仍未接入；跨机器的人工 Hook 审核、真实图片工具契约和最终人脸相似度仍需在未参与开发的 Codex 环境人工验收。

因此它可以公开查看和邀请开发者试用，但暂时不应宣传为已经稳定的普通用户虚拟伴侣产品。
