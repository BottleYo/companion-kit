# Companion Kit 产品逻辑

## 这次只解决 Codex

Companion Kit 的长期目标仍是让常用智能工具都能安装一个轻量陪伴层，但当前版本只把 Codex 当作产品目标。OpenClaw、Hermes 与 Claude 的已有适配不删除，也不在本轮增加功能。

各宿主继续保存各自独立的 Persona、关系和图片目录。本轮不设计统一 Persona，也不做跨宿主同步。

Codex 适合作为第一站，因为它已经有成熟的任务能力和内置图片生成。项目只需处理三件事：人物是谁、关系如何影响闲聊、怎样稳定地生成同一个人物，而不必再造一套聊天和工具平台。

## Persona 是一张轻量人物面板

Persona v3 不再只有 `soul + memory`。它分为几组用户容易理解、程序也能稳定读取的信息：

- 人物总意图：用户最初用一句话描述的期待；
- 表达层：称呼、性格、说话方式、背景基调、重视的事、兴趣和边界；
- 任务层：遇到代码、分析和其他正事时怎样协助；
- 外观层：人物气质与照片默认风格；
- 身份层：是否已经确认脸部身份、身份版本和唯一参考 ID；
- 关系层：相处起点、关系方向和当前多维投影；
- 来源层：哪些字段由系统补全，哪些字段由用户亲手修改。

初始化允许两种入口。用户可以从模板开始，也可以直接输入“高冷御姐，成熟自信，解决问题利落”这样的描述。补全器会生成一份相互协调的草稿，先预览，再由用户确认保存。模板只是起点，不是角色清单。

用户改过的字段会进入 `user_fields`。下次根据新描述重新补全时，这些字段默认保留，避免一次重算把用户慢慢调好的设定覆盖掉。

外观身份是可选项。保存 Persona 后，用户可以直接在面板上传一张参考图；不知道想要什么长相时也可以跳过，直到第一次自然地请求照片。

## 任务质量防火墙

Persona 是表达上下文，不是新的执行器。Codex Runtime 明确要求：

- 代码正确性、事实、安全、测试和用户当前技术要求优先；
- Persona 只改变不关键的表达，不改变工具选择和技术判断；
- 不把背景基调扩写成虚构的现实履历或共同经历；
- 不依赖、不读取也不修改 Codex 全局个性化与记忆设置。

因此同一个对象既可以自然闲聊，也可以继续完成 Codex 原来擅长的任务。

Persona 不再默认进入所有任务。用户说“把这个任务设为陪伴任务”后，当前任务才会持久加载 Persona；说“退出陪伴任务”后立即停止加载。绑定层只保存任务标识的本机 HMAC，不保存原始任务 ID 或聊天正文，读取异常时按未绑定处理。普通任务仍可明确请求一次人物照片，这种单次照片不会顺手把任务变成陪伴任务。

## 关系是多维投影

长期关系由熟悉度、信任度和亲近度组成，短期气氛单独保存并带有效期。关系变化依赖少量结构化事件，同类事件有冷却时间，每天有变化上限。

关系投影只影响闲聊的主动程度、称呼和照片表达上限，不影响任务答案的正确性。长期维度不会因为几天没聊天机械下降，一次小摩擦也不会永久改变所有状态。

当前版本已经能读取和投影关系，但还没有从真实聊天自动产生关系事件。下一阶段的事件提取器只能提交事件类型、置信度、时间和不透明作用域，不得保存聊天正文，也必须区分“用户在抱怨代码”和“用户在表达对人物的不适”。低置信度事件拒绝写入。

## 固定的是脸，不是造型

图片身份和普通成图分开管理。

当 Persona 还没有固定脸，可以在面板直接选择参考图，也可以等第一次照片请求再进入轻量确认流程：

1. 用户上传有权使用的成年人物或虚构形象参考；或
2. 用户描述想要的感觉，由 Codex 内置生图生成；或
3. 由人物根据 Persona 自己决定候选。

面板入口先在浏览器显示预览，转换成 PNG 后进入本地候选槽；聊天入口先在当前任务展示候选。两条入口都不会自动固定，只有用户明确确认后，候选才会成为当前身份版本的主脸参考。Persona v3 仍只保存这一条主脸 `reference_id`，不把侧脸、体型或真实路径写进人格配置。

已有主脸时，面板允许随时发起一次显式更换。新照片在确认前只占用下一身份版本的候选槽，当前身份继续生效；确认后 Persona 只把 `identity_version` 前进一位并绑定新主脸。人物设定、关系数据、PhotoMoment 历史和旧 Identity Pack 都不删除。新身份从只有主脸的基础包开始，旧版本的侧脸与体型不会跨版本混用；最近图片回执也绑定身份版本，因此旧任务成图不能冒充新身份的编辑底图。切换后的新形象要由下一个 Codex 任务加载。

私有图片资产层以 `profile_id + identity_version` 保存一个轻量 Identity Pack：一张必需主脸，以及可选的一张侧脸和一张体型参考。初始化和首次确认不要求三视图；用户明确要求提高稳定性时，才基于主脸逐张生成补充候选，仍需展示并确认。普通日常成图不得自动收入身份包。

后续任务平时只加载轻量 Persona。真正出现人物照片请求时，`UserPromptSubmit` 才安全解析当前 Identity Pack，把已验证的角色和本地 PNG 路径放进当轮私有上下文。图片调用前，`PreToolUse` 会重写实际工具参数：普通自拍只使用主脸；明确侧脸时使用主脸加侧脸；全身、穿搭、姿势或远景使用主脸加体型；同时涉及侧脸和全身时优先体型。每次最多两张且主脸必带，不把三张同时注入。

未配置可选角色不算错误，继续只用主脸。身份包已经声明的任一成员缺失、损坏、被替换或与当前 Persona 不匹配时，整包失败关闭，不允许忽略损坏成员、跨版本查找或用纯文字重建另一张脸。真实图片工具是否实际接收所选参考，需要单独的端到端验收，不能只凭上下文字符串判断成功。

身份约束只覆盖稳定面部结构、辨识特征和经确认的稳定体型特征。发型、表情、妆容、服饰、姿势、镜头、场景与光线都是动态呈现，应随本次需求变化。PhotoMoment v3 新增一条独立的面部动态轴：情绪只决定大方向，面部动态再明确头部角度、视线、眉眼和嘴角。最近四张会参与去重，避免参考图把每次照片都拉回同一个正头、直视和标准微笑。用户点名的细节始终优先。

身体可见时，默认使用偏高挑、修长但解剖自然的成年人比例，并明确约束头身、肩颈、躯干和镜头透视。高挑感来自自然骨架、站姿、穿搭和构图，不靠缩小头部、暴力拉腿或统一瘦脸；用户设定或已确认的体型参考优先。当前不做隐藏试拍或自动相似度打分；成图如果明显像另一个人，只在用户明确要求后使用同一组参考重试。

妆容变化遵循生活连续性，不是每张强制轮换。同一组或明确接着拍时沿用当前妆容；连续多次相同且时间、场景或准备状态发生变化时，才从轻量枚举中自然换一个方向。用户明确点名的发型、表情、面部动态或妆容始终优先并退出自动轮换。旧版 PhotoMoment 没有妆容或面部动态字段时按“未指定”读取，直到下一次成功照片再无损写入新版历史。

参考图复用可以显著提高一致性，但生成模型不能保证数学意义上的像素级同一。本地资产层能强制唯一身份包、清单完整性和损坏失败关闭，`PreToolUse` 也把实际工具输入限制为一至两张权威参考。自动测试已经覆盖参数重写；不同 Codex 版本是否仍使用相同工具契约，以及最终相似度如何，仍要做真实端到端验收。

## 每日 OOTD 是一层服饰连续性

人物外观按四层合成：Identity Pack 固定脸；Persona 提供长期衣橱方向；Daily Look 安排今天这一套；PhotoMoment 决定这一张照片的发型、表情、面部动态、妆容、动作和镜头。这样同一天有连续感，又不会连续几张只换背景。

“一天”以本机时区凌晨 4 点为界。系统没有定时任务，也不会半夜调用模型：当天第一次在已绑定任务里问 OOTD，或第一次请求固定人物照片时，才用 Persona 风格、本地主题和配色组件安排一张结构化穿搭卡。卡片只含主题、气质、配色、轮廓、核心单品和一个点睛细节；最近 30 天留在本机，14 天内不重复完全相同的组合。

优先级很简单：用户本张照片的明确要求最高；“今天换一套”会替换当天主题；“只这张这样穿”只影响这一张；没有新要求时沿用当天主题；最后才回到 Persona 的默认衣橱。关系亲近不自动让衣服变得更暴露。发型、表情和妆容也不属于 OOTD，不会被一件衣服顺手焊死。

穿搭卡先是 `planned`。只有图片工具真的返回人物照片，卡片才变为 `confirmed`；失败、取消或普通图片不会留下“已经穿过”的假记录。编辑上一张时保留目标照片里的服饰，不趁机改写当天主题。图片后的文字可以接住画面里确实出现的一处穿搭细节，但不能照着卡片念清单。

在已绑定任务里，Hook 刚提供今日穿搭，或刚收到一张真实人物照片后，会写一条十分钟有效的一次性续拍状态。它只含任务摘要、Persona 摘要、来源、时间和可选穿搭卡 ID，不保存聊天原文。于是下一句“拍吧”“那就拍吧”可以继承当前穿搭并走完整照片链路；消费一次、退出陪伴任务、切换 Persona 或明确转去普通工作时立即失效。没有这条状态时，单独的“拍吧”仍按普通文字透传。

人物面板提供“安排今天、换一套、按一句话微调、记住这种感觉、暂停”五个直白操作。打开面板只读状态，不会悄悄安排新衣服。偏好只让某类主题以后更容易出现，不会每天复制同一套。

## Codex 图片只有一条路径

人物候选、日常照片和参考图编辑都使用 Codex 内置图片生成。Codex 官方说明中，内置能力使用 `gpt-image-2` 并计入现有 Codex 使用额度。

Companion Kit 的 Codex 路径：

- 不读取或索要 `OPENAI_API_KEY`；
- 不展示 Provider、快速/严格模式或独立 API 付费确认；
- 当前 Codex 图片工具不暴露 `moderation` 参数，因此审核级别由宿主管理；项目不会假装设置成功，也不会把参数塞进提示词；
- 不让用户编写图片提示词；
- 场景不明确时，由人物在 Persona、关系和安全边界内选择普通生活场景；
- 场景明确时直接生成，不重复追问服装、动作和模型参数；
- 没有真实图片结果时，不声称已经拍好或发送成功。

从聊天进入候选槽时，暂存和确认命令只在照片回合私下提供给 Codex，用当前 `session_id` 作为不透明任务作用域。图片工具完成后，专用 `PostToolUse` Hook 只从工具回执提取 `generated_images` 路径，并保存任务、路径、内容和工具调用的哈希。暂存时必须消费同一任务的单次回执；旧任务图片、被替换文件和重复消费都会失败。内部命令、资产 ID、本地路径和图片提示都不得进入人物回复。

面板上传不伪造图片工具回执。浏览器只处理用户当次选择的 PNG、JPG 或 WebP，限制原图大小和最长边，重绘为 PNG；写入接口同时要求本次面板令牌、同源请求和图片使用权确认。服务端只接收图片字节，不接收任意文件路径，并在保存前再次执行 PNG 解码、尺寸限制和元数据清洗。确认主脸使用与聊天入口相同的提交与回滚逻辑。

## 为什么使用窄 Hook

Skill 适合显式调用一项流程，陪伴对象却应该在普通对话开始前已经存在。每次先输入 `$virtual-companion`，产品会立刻变成“调用功能”。

Codex Plugin 使用四个窄 Hook。`SessionStart` 总会留下最小健康回执，但只有任务已经显式绑定时才注入压缩 Persona；`UserPromptSubmit` 只识别绑定、退出、明确的今日穿搭提问、受控短句续拍和人物照片请求，不匹配就零输出；`PreToolUse` 只有在照片票据、当前回合控制信封和 Persona 全部匹配时才改写参考图参数；`PostToolUse` 登记真实图片结果，并把当张照片与穿搭的文案线索交回 Codex。普通图片仍可留下短期原生回执，方便用户明确选作人物候选，但不会写入 Persona 照片历史。

Plugin 安装状态与运行就绪状态是两回事。人物面板按顺序区分：未安装；待用户在 `/hooks` 审核；等待新任务验证 `SessionStart`；尚未创建 Persona；尚未绑定陪伴任务；绑定任务尚未加载当前 Persona；人物聊天与主脸已经加载。Codex 没有给面板安全的信任查询接口，因此真正的运行证据只能来自 Hook 自己的健康回执。

`SessionStart` 回执只证明 Hook 已运行；单独的 `companion_context` 回执才证明某个已绑定任务实际加载过 Persona。面板会把后者的时间与 Persona、Identity Pack 修改时间比较。Plugin 版本或 Hook bundle 内容变化时，旧审核进度和回执自动过期。`PostToolUse` 在第一次真实图片结果登记后单独验证，不阻塞已经确认的主脸。

Hook 的失败边界是：

- 没有配置时不向任务输出 Persona 内容，但仍可写一张不含私人数据的 `SessionStart` 健康回执；
- 配置损坏时不阻断 Codex；
- 不设置可见状态消息；
- 只有陪伴任务才加载常驻上下文，并限制在 1400 字符以内；身份路径、照片配方、今日穿搭和候选命令只在人物照片回合按需加载，并限制在 3600 字符以内；
- 图片回执只保存哈希和时间，最长保留两小时，不保存原始任务标识或绝对路径；
- 照片回合票据只含受控模式、不透明摘要和时间，二十分钟失效；最近图片类型摘要同时绑定路径与文件内容哈希，两小时失效。已签发的人物编辑票据在任一核验失败时停止，不降级为普通图片编辑；
- 路径只进入模型私有上下文，不在用户回答中展示；
- 安装或变更后仍需用户按 Codex 官方机制检查并信任 Hook。
- 健康回执只保存 schema、Plugin 版本、Hook bundle 摘要、Hook 类型和最近成功时间；不保存聊天、提示词、任务 ID 或参考图路径，也不写入 `trusted_hash`。

Codex Plugin 不再暴露独立诊断 Skill。配置和状态检查由 Plugin 自带的本地 MCP Server 返回，并在 Codex Plugin UI 中渲染；没有独立 App Server，也不访问外网。源码中的 Skill 只保留给 OpenClaw、Hermes 和 Claude 的兼容安装。

## 保持轻量的方法

- Codex Plugin UI 负责创建、查看、调整 Persona，并在本地预览、确认或更换一张主脸；
- Persona 使用版本化 TOML，关系使用结构化 SQLite，不建立聊天数据库；
- 每个身份版本只保留一个候选槽和一个最多三张、角色固定的轻量 Identity Pack，不做图库；只有 Persona 指向的版本参与新照片，旧版本仅为安全恢复保留；另外只保存最近四条受控 PhotoMoment 和最近 30 天结构化 Daily Look，用于保持合理连续性，不保存图片或聊天；
- 生成仍由 Codex 完成，项目不再包一层图片 Provider；
- Content Studio 等较重项目只提供分层思路，不复制其工作流和数据模型；
- 当前迭代不为了未来多宿主抽象而增加 Codex 用户看不懂的配置。

## 当前诚实边界

`0.9.0-dev.3` 在上一版每日 OOTD、自然人体比例和面部动态基础上，补上了连续对话里的短句续拍。它不增加图片调用、后台任务或 Provider 配置。Plugin UI、任务隔离、身份保护、图文联动和安全升级继续保留；Codex 图片审核参数仍由宿主管理。

自动关系事件、Git 来源自动更新和自动卸载尚未接入。Plugin UI 已通过协议级测试，但还要在另一台安装最终版本的 Codex 上完成人工渲染、Hook 审核、真实图片工具参数和人脸一致性验收。

因此它可以公开查看和邀请开发者试用，但暂时不应宣传为已经稳定的普通用户虚拟伴侣产品。
